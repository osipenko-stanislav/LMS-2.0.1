# LMS 2.0.1 — Architecture

## Принцип

Данные, бизнес-логика, композиции и визуальное представление развиваются независимо.

Страницы и Generative UI переиспользуют компоненты, контракты, данные и действия. Представление адаптируется к контексту диалога и не обязано повторять экранную композицию. Общий renderer используется для поддерживаемых типов блоков.

## Слои

**Data & Content**

- Доменные сущности, fixtures, репозитории и адаптеры источников.
- Структурированные данные и текстовый контент хранятся отдельно.
- Источник данных можно заменить без изменения UI.
- Происхождение демонстрационных и AI-сгенерированных данных фиксируется в метаданных. Технические подписи о демонстрационных данных не выводятся в пользовательском интерфейсе.

**Domain**

- Бизнес-правила, операции, состояние продукта.
- Действия имеют типизированные идентификаторы и payload.
- Доменный слой не зависит от React и UI-компонентов.

**Contracts**

- Типизированные описания данных для отображения, состояний, действий и параметров блоков.
- Контракты не содержат JSX и конкретных источников данных.
- TypeScript-типы в коде являются источником истины.

**Primitives**

- Базовые компоненты Linear UI и их стандартное UI-поведение.
- Не содержат предметной логики и запросов к данным.

**Compositions**

- Переиспользуемые блоки, собранные из примитивов.
- Поддерживают типизированные props, slots, variants и events.
- Не обращаются напрямую к репозиториям и API.

**Renderer & Views**

- Registry связывает типы блоков с их реализациями.
- Renderer отображает композиции по контракту.
- Страницы и Generative UI используют общий renderer только для поддерживаемых типов блоков; это не требует перевода всех экранов на него.
- Layout управляет размещением, а не предметной логикой.

**Workspace layout**

- `WorkspaceFrame` управляет внешней геометрией страниц и области диалога; блоки Generative UI адаптируются внутри неё без вложенной экранной layout-системы.
- `WorkspaceFrame` принимает режим `reading`, `workspace` или `data`, управляет внешними отступами, центрированием, общей осью заголовка и контента, а также дополнительным contextual rail.
- Страницы не создают собственные параллельные layout-системы, наборы режимов ширины или повторяющиеся правила центрирования.
- Основная колонка центрируется относительно доступной области Workspace, а rail располагается рядом и не входит в её `max-width`.
- При изменении ширины Sidebar и viewport доступная ширина Workspace пересчитывается контейнером.
- На мобильных Sidebar открывается через Dialog/Sheet и не занимает постоянную rail-полосу.
- Если rail не содержит данных, под него не резервируется пустая колонка; при нехватке места rail переходит в overlay или доступное panel-состояние.

## Направление зависимостей

Data → Domain → View Contracts → Compositions → Renderer → Views.

Это схема потока данных, а не разрешение нижним слоям импортировать верхние.

Запрещены циклические зависимости и прямые обращения UI к хранилищам.

## Изменения интерфейса

- Состав и порядок блоков определяются конфигурацией View, если существующий механизм и контракт это поддерживают; не создавай инфраструктуру конфигурации без конкретной необходимости.
- Состав контролов определяется поддерживаемыми слотами композиции.
- Новая функция сначала использует существующие контракты и действия.
- Расширяй контракт только при наличии конкретного сценария.
- Не создавай универсальный DSL, runtime-evaluator или параллельный renderer.

## Generative UI

- Beautiful UI служит поведенческим референсом; его демонстрационные таймеры не заменяют реальные события AI и инструментов.
- AI-интеграция передаёт структурированные данные, а не JSX. Разрешённые типы блоков, их props и действия проверяются до отображения; неизвестные и некорректные блоки получают безопасное текстовое представление.
- Визуальный слой отображает состояния loading, streaming, error, success и interactive из контроллера; бизнес-операции выполняются через существующие действия приложения. Текстовые дельты и завершённые валидные блоки обрабатываются раздельно.
- Composer — общая управляемая композиция: ввод, панель действий, превью вложений и состояния. История, загрузка файлов, AI-транспорт и выполнение действий остаются вне визуального компонента.
- AI выбирает только зарегистрированные типы блоков и допустимые действия.
- Описания AI-композиций проходят валидацию.
- AI не выполняет произвольный код и не создаёт обработчики.
- Доступные действия определяются приложением, а не моделью.
- AI-сгенерированный контент не подменяет данные из доверенных источников.

## Проверка архитектуры

В рамках возможностей существующего контракта изменение конфигурации должно позволять:

- Переставлять блоки.
- Добавлять и удалять поддерживаемые контролы.
- Переиспользовать поддерживаемые блоки на странице и в Gen UI, адаптируя композицию к контексту.
- Заменять источник данных без изменения визуальных компонентов.

Не вводи инфраструктуру без работающего сценария, который её требует.

## Сквозные сущности и единый источник истины

- Доменные сущности, используемые несколькими разделами, определяются в отдельных модулях `src/core/domain/`.
- Каждая сущность имеет единый типизированный контракт, стабильный идентификатор и явно определённые связи.
- Общие данные, контент и fixtures хранятся отдельно от визуальных компонентов.
- Компоненты не содержат собственных копий доменных моделей, справочников, статусов и демонстрационных данных.
- Страницы и Generative UI используют одни и те же сущности через View Contracts.
- Изменения сущности должны согласованно отражаться во всех её представлениях.
- Локальное UI-состояние, не имеющее предметного значения, может оставаться внутри компонента.
- Не создавай отдельный файл для каждого вспомогательного типа: выделяй самостоятельные и переиспользуемые сущности.

При изменении существующей структуры сохраняй работающие контракты и избегай массового рефакторинга без необходимости.
