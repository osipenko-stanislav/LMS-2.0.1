# Beautiful UI и Generative UI в LMS 2.0.1

Дата: 23 ноября 2026 года. Отчёт для передачи контекста GPT и дальнейшего обсуждения реализации.

## Итог и границы выполненного

Beautiful UI рекомендуется использовать как источник интерактивных AI-native UX-паттернов, а не подключать как дополнительный UI-kit. Исследованы сайт, исходники двух репозиториев и текущая архитектура LMS. Правила использования зафиксированы в существующей документации. Вынесен и подключён единый системный Composer на существующих примитивах Linear.

Другие компоненты Beautiful UI не перенесены. Зависимости не устанавливались. Реальная AI-интеграция, streaming, загрузка файлов, реестр AI-блоков и операции изменения учебного плана в рамках этой задачи не реализовывались.

## Зафиксированные правила проекта

Изменены [AGENTS.md](AGENTS.md), [DESIGN.md](DESIGN.md) и [ARCHITECTURE.md](ARCHITECTURE.md):

- Linear/DesignKit и Woblo определяют визуальную систему; существующие компоненты Linear UI остаются технической основой.
- Woday — композиционный ориентир.
- Beautiful UI — источник UX-паттернов, интерактивных состояний и композиции AI-native компонентов.
- Паттерны адаптируются к существующим компонентам, токенам и архитектуре LMS; стилистика и зависимости не переносятся автоматически.
- AI-интеграция должна передавать структурированные данные, а не JSX; данные и допустимые действия проверяются до отображения.
- Демонстрационные таймеры библиотеки не заменяют реальные события AI и инструментов.
- Composer отвечает за представление ввода; история, транспорт, загрузка файлов и бизнес-операции остаются снаружи.

Эти архитектурные правила описывают требования к развитию Gen UI. Они не означают, что вся соответствующая инфраструктура уже существует в коде.

## Подтверждённые особенности исходников

Первый репозиторий предоставляет больше параметров и callbacks. Во втором многие компоненты содержат встроенные примеры данных. Ни один из них сам по себе не предоставляет готовую AI-интеграцию LMS.

- **Approval Card:** вопросы, одиночный/множественный выбор, свободный ответ и прогресс. Radio-выбор запускает автоматическое продвижение через 480 мс. Для изменения данных LMS требуется отдельное явное подтверждение. Передача свободного ответа должна быть отдельно проверена при адаптации: наличие поля не гарантирует включения его значения в payload операции.
- **Task Rows:** раскрываемые детали, индикаторы и статусы. В демонстрации часть последовательности определяется таймерами; это не события реального инструмента.
- **Tool Chips:** компактные шаги, раскрытие деталей, сводка изменений и предпросмотр. Появление шагов в демонстрации также управляется таймерами.
- **Context Cards:** выдержки и подписи источников. В адаптации источник должен иметь реальную ссылку или идентификатор сущности, а интерактивный элемент — подходящую семантику.
- **Diff Table:** визуализация добавлений/удалений и выбор изменений. В изученной реализации есть демонстрационные таймеры, встроенные ключи примеров и локальное состояние принятия; это не универсальная транзакционная операция.
- **Insight Cards:** мини-визуализации, переключение метрик и взаимодействие с графиками; используются `liveline` и локальные визуальные соглашения.
- **Recommendation Card:** выбор рекомендации и локальное принятие. Это не подтверждение успешного выполнения серверной операции.
- **Streaming Text:** последовательное отображение токенов через таймер; в Beautiful UI `loop` по умолчанию включён. Это имитация потока, а не сетевой streaming.
- **Thinking:** раскрываемые этапы и представление работы; реальные события процесса нужно передавать извне.
- **Chat Composer:** поле ввода и нижняя панель отправки внутри демонстрационного чата. Используется однострочный `input`; ответы появляются по сценарным таймерам. Многострочный ввод, upload pipeline и история LMS этим компонентом не обеспечиваются.

Технологии: React, TypeScript, Tailwind, Next.js для сайтов. В `beautiful-ui` также объявлены Motion 13, собственные атомы, иконные пакеты, `liveline`, `glimm` и другие зависимости; во втором репозитории — Next.js 16, React 19, `iconoir-react`, `liveline`, `glimm`. Зависимости приложения-каталога нельзя автоматически считать обязательными для каждого отдельного компонента. Для предлагаемых адаптаций LMS новые пакеты сейчас не обоснованы.

## Предлагаемая минимальная архитектура Gen UI

Это предложение, а не выполненная интеграция.

1. **AI-адаптер:** принимает запрос и контекст, отдаёт текстовые дельты, события инструментов и завершённые структурированные блоки. Не передаёт JSX, обработчики или исполняемый код.
2. **Контракты и валидация:** точечно расширить существующий `ChatBlock` как discriminated union. Проверять тип, обязательные поля, размеры массивов/текста, идентификаторы сущностей и разрешённые действия. Валидировать также данные после загрузки сохранённой истории. Некорректные/неизвестные блоки заменять безопасным текстовым представлением.
3. **Реестр:** небольшое соответствие разрешённых типов существующим композициям. Использовать его только для поддерживаемых Gen UI-блоков; не переводить все страницы на новый renderer.
4. **Контроллер:** хранит loading, streaming, error, success и interactive states, порядок событий и состояние текущего запроса. Текстовые дельты обрабатываются отдельно от завершённых валидных блоков. Отмена должна прекращать реальный запрос, а не только менять иконку.
5. **Действия:** навигация через текущий `navigate`, бизнес-операции через существующий dispatch. Расширять `Action` только под согласованный сценарий. Проверять права и актуальность операции в исполнительном слое; модель не определяет доступность действия.
6. **Представление:** существующие Linear-примитивы и общие композиции. Данные и обработчики поступают извне. Ширина ограничена колонкой чата, широкие таблицы прокручиваются внутри блока.

Для операций изменения плана нужны preview, явное подтверждение, защита от повторного выполнения и фактический результат операции. Эти возможности нельзя считать реализованными через локальный `accepted=true` сторонней карточки.

## Первая итерация

| Приоритет | Компонент | Сценарий | Критерий готовности |
| --- | --- | --- | --- |
| 1 | Composer | Единый ввод в Навигаторе и компактном AI-представлении | Один компонент, сохранённые обработчики и история, корректная клавиатура и мобильный рендер; базовая работа выполнена |
| 2 | Context Cards | Открыть источник, на котором основан ответ | Источник существует, переход работает, выдержка соответствует данным, длинное название не ломает блок |
| 3 | Approval Card | Уточнить предпочтения или подтвердить изменение | Все выбранные и свободные ответы входят в payload; операция выполняется только после явного подтверждения |
| 4 | Task Rows / Tool Chips | Показать этапы подбора материалов или построения плана | Статусы соответствуют реальным событиям; раскрытие доступно с клавиатуры; ошибки не маскируются таймерами |
| 5 | Streaming / Thinking | Показать ожидание и поступающий ответ | Нет искусственной задержки токенов; отмена работает; скролл не мешает чтению; ошибки сохраняют возможность повторить запрос |

Diff Table — следующий этап после появления реальной операции изменения плана. Аналитические и Recommendation Cards — после определения сценария и надёжных исходных данных.

### Ограничения реализации

Composer управляемый: он не загружает и не сохраняет файлы, не владеет AI-транспортом и не выполняет retry самостоятельно. Родитель передаёт актуальные состояния и обработчики. Превью получает готовый URL; создание, безопасность и освобождение object URL относятся к слою загрузки.

В Навигаторе подключён текущий текстовый сценарий. Вложения, остановка и состояния генерации представлены контрактами и Storybook, но не подключены к реальному backend. Кнопка вложения не показывается без `onAttach`, остановка — без `onStop`. Отправка только вложения без текста сейчас не поддерживается. `onSend` не ожидает Promise: асинхронный процесс должен управляться владельцем.

Реальный streaming отсутствовал до изменения и не был добавлен. Нельзя описывать текущую работу как проверенный end-to-end AI-чат.

## Указания для дальнейшей работы GPT

Сначала сверить актуальный код и правила: этот отчёт — снимок состояния, а не доказательство будущего поведения. Не устанавливать Beautiful UI или её зависимости автоматически. Не создавать второй Composer, UI-kit или параллельный renderer. Следующий шаг — согласованный сценарий Context Cards или Approval Card с реальными данными и действиями; AI-транспорт и изменения плана требуют отдельного объёма реализации.
